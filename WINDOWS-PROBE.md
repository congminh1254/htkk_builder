# HTKK Windows readiness probe

Prepared for a separate public repository. Dispatch only; default verifies sources and prerequisites without installing. No workflow has been run by preparing these files.

This probe downloads the public GDT-linked Fshare RAR and known mirror ZIP, verifies pinned SHA-256 for both archives, compares both Data1.cab SHA-256 values against the independently observed official-distribution cabinet, pins the MSI SHA-256, then requires Windows Authenticode `Valid`, expected publisher name/certificate serial, a timestamp certificate and successful Windows SDK SignTool `/pa /all /v` verification. Any missing verification tool blocks installation.

The archive provenance is documented separately in the application repository. RAR and ZIP hashes differ because their containers differ. The CAB matches both distributions. This does not mean the CAB has its own signature or that software is risk-free.

Existing .NET 3.5 must be enabled and installed. Missing .NET stops the probe; no bundled bootstrapper is run and Windows feature installation is not attempted. This is expected to expose an external dependency on some hosted images. `windows-latest` image behavior and HTKK interactive startup are not yet tested.

Only an explicit dispatch input can authorize the installation branch, after all gates. It calls `msiexec /qn /norestart`, disables the installer's update flag, and logs only to temporary runner disk. Before HTKK startup, a Windows firewall outbound rule blocks the application. No taxpayer code or other data is entered. Only process-alive/window-observed booleans are reported; these are readiness observations and never output/round-trip compatibility proof.

The public job has read-only repository permission, disables persisted checkout credentials, uploads no public artifacts and creates no cache. The GUI/probe step accepts no credential; a separate final step may use the source token only to publish a tightly scoped startup diagnostic to the fixed PRIVATE htkk_web repository. Raw extraction/signature/MSI logs stay in a temporary directory removed at exit. A screenshot may be captured only from an owned fresh descendant, Authenticode-valid Microsoft System32/SysWOW64 regsvr32.exe process with the exact RegSvr32 #32770 modal. No full-desktop or arbitrary-window fallback exists; no taxpayer data is entered. At most one 2000×2000/2 MB PNG and allowlisted metadata are uploaded to the private windows-reference-diagnostics branch after verifying the target repository is private. This branch is temporary diagnostic storage, never main/pages-output; no raw window title/text or pixels enter public Actions logs or artifacts. The local capture is removed after publication. Startup/window evidence never proves XML compatibility. The disposable GitHub runner is destroyed afterward.

Public output is a fixed JSON schema with version, gate booleans, stage, installer exit code and an allowlisted block reason. Network/tool error details, redirect URLs, cookies, installer text, machine paths, login data and environment variables are not printed. The workflow uses no relay token. Public URLs are accessed directly by the hosted runner with normal TLS.

Before dispatch, review the script in the public builder repository and verify the official publication still links to the pinned source. Pin third-party GitHub Actions to a reviewed commit if repository policy requires it. A dependency/image/source change requires a new provenance review; never relax the hash or Authenticode checks to make the probe pass.

When registration acknowledgement is enabled, the probe first posts IDOK to the exact owned Microsoft RegSvr32 modal and waits one second. If the retained process still runs, it revalidates fresh ancestry and Microsoft image identity, then may post WM_CLOSE once to that SAME HWND retained privately from the IDOK attempt. This is based on the private successful TBarCode5.ocx registration popup observation; it is not permission to close unrelated dialogs or send Yes. The process must still exit with code 0; a nonzero or unavailable result blocks the gate. Fixed counters distinguish IDOK and close fallback attempts; no handle or raw popup text is published.

Optional `synthetic_login` uses only the fixed checksum-valid fake MST 9999999997 on the retained original GUI root. The helper requires the source login form's exact Mã số thuế label, unique enabled combo, Mã số mới button and Đồng ý button (source Text is Đồ&ng ý). It posts Mã số mới, sets and reads back the fixed combo text, then posts Đồng ý. It waits at most about 20 seconds for login to hide and the source profile caption to appear in an owned top-level or MDI child window. Native discovery and reads are bounded; only class-category counts, allowlisted static labels and fixed status booleans leave the helper. A profile caption observation is not validation of profile fields or any XML export/import round trip. No bundled taxpayer sample is reused and no arbitrary user-supplied text is accepted.

For a blocked synthetic login transition only, a second private diagnostic scope may capture the foremost visible original HTKK root-owned WinForms/native modal window after new-ID click, verified fixed synthetic input, login click, login hiding and fresh fixture-directory creation are all established. It rechecks the retained root start time, exact original executable path, pinned executable/config hashes, and writes only `synthetic-login-window.png` plus strict allowlisted metadata. Custom reference hosts are excluded from this scope. The original application may display bundled defaults; the image is explicitly NOT claimed entirely synthetic. No actual user taxpayer input is provided, no desktop fallback exists, and the same fixed private branch/size limits apply. These windows are observed, not automatically confirmed.

The original new-MST profile opens in a generic main window titled Hỗ trợ kê khai thuế - Phiên bản 5.8.1, not necessarily a window captioned with the Menu100_1 label. Following the established fresh synthetic login sequence, the gate may recognize this exact normalized main caption, unique enabled Ghi and Đóng buttons, and at least one visible managed WinForms container. Native generic WinForms HWNDs are reported as `managed-window`, not falsely asserted to identify FarPoint. This structural observation is grounded in original ThemMSTMoi's Menu100_1 flow and the private profile image; it does not validate profile content, saving or XML export.
