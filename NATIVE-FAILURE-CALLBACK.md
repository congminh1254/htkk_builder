# Report preflight/whole-job failure from an isolated runner

The Windows workflow previously reported a fixed native case only after `native_probe` emitted `credentials_safe=true`. A preflight failure before that step left the status queued forever. Example40795709227/job123191570690: the clean Framework UIA fixture timed out at `types-loading`, process stopped verified, before supplier launch. Source898627e retained a pending sale5-manual status; Pages40795757842 waited20minutes and failed. This is not a tax/XML mismatch, and no timeout or native acceptance rule is relaxed.

A separate `report_failure` job now runs on a fresh Linux runner when the Windows readiness job fails/cancels. It checks out only this trusted public repository and executes a failure-only callback. No supplier, private source, XML, diagnostic file or build output is executed or transferred into this job. A process from the Windows job cannot access the Linux job's status credential. Existing supplier-side publication still requires verified cleanup.

`report-native-failure.py` accepts only this builder's main, the fixed thirteen-case allowlist, full source SHA, bounded run ID, official GitHub origin and failure/cancelled outcome. Its output can only be a failure status in the fixed private source repository. It cannot turn a native failure into success or downgrade an otherwise successful readiness job. A post-step failure after the early success callback is also reflected as failure. Global platform cancellation/unavailability or an API outage may prevent any scheduled callback; no success is inferred in that situation.

Unit checks exercise all cases and reject success/pending outcomes, foreign origins/repos/branches/modes, unknown cases and malformed identities before authenticated I/O. Windows/native success evidence and an isolated intentionally rejected-input integration case must be linked in review401. The negative case is not native qualification and must not be counted among the13positivecases.
